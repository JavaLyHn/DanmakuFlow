# 本地页面一键启停后端设计

状态：方案方向和停服范围已由用户选择，设计已完成只读可实施性审查，等待用户确认实施；尚未实施或启动基础设施。

用户已补充确认：同时设计“停止本次启动的服务”，不停止原本已运行的服务；补齐 Go 服务退出处理，避免直接强杀。

## 目标和范围

用户希望从现有直播间页面启动本机后端，不再分别打开终端执行 MySQL、Redis、Kafka、消费者和服务端的命令。用户已选择“前端页面显示启动按钮，由独立本地启动器执行”。本项目继续以 Go 为主线，Java 保持暂停。

本轮面向用户当前的 Windows 开发机，提供启动、停止、状态、失败原因和重试。复用现有 Vue 页面、Go 服务及本机已安装的依赖，不引入 Docker、Electron、额外数据库、进程管理平台或压测工具。页面的弹幕、点赞、房间和视频占位行为保持现状。

不把服务启动成功称为全链路读写测试通过，不把健康检查变成测试消息写入。服务真正运行后，已有消费者可能消费 Kafka 中的历史积压，这是正常业务运行，不是只读验证。

## 考虑过的方案

1. 双击脚本直接启动全部服务并打开页面：实现较少、无额外常驻控制服务，是助手最初推荐的简化方案；用户没有选择此方式。
2. 独立本地启动器托管页面，由页面按钮启动服务：用户已选择。多一个轻量进程，但后端停止时页面仍能打开、显示进度与错误。

不能仅在现有 Go 服务的 8080 页面添加启动自身的按钮，因为服务未运行时无法提供该页面。普通网页也不能独立执行本机程序，需要本地启动器承担进程操作。

## 使用过程

首次准备一次本机路径与数据库连接配置，并构建页面、启动器及两个业务程序。数据库需已创建，缺失表由独立的 `cmd/migrate` 显式初始化；启动按钮不自动初始化。

之后的日常操作：

1. 双击仓库的 `启动本地页面.cmd`（名称为设计建议），启动或复用本地启动器，自动打开浏览器。
2. 页面仍是现有直播间，顶部增加一小块“本地后端”区域；点击“启动后端”。
3. 页面显示逐项进度，依赖检查与业务启动完成后显示“后端已就绪”。
4. 用户点击已有的“连接房间”，进行弹幕互动。启动后端不会自动加入房间、发送弹幕或改变 UID。
5. 使用完点击“停止本次启动的服务”，查看停止进度和保留运行的已有服务。停止完成后页面仍可打开，再次点击启动即可使用。

刷新页面、关闭标签页不会停止后端；再次打开可以继续查看状态。关闭页面不是停止服务的操作。启动器意外退出也不强制结束其子进程，重新打开时核对原进程身份后恢复状态。

## 页面

新增一个小型区域，不新建管理后台或路由：

- 一个主按钮：启动后端 / 启动中… / 后端已就绪；失败后为“重试启动”。启动中禁止重复提交。
- 一个停止按钮：“停止本次启动的服务”；停止中禁止重复操作，超时/失败后显示“重试停止”。没有自己启动的服务时禁用并说明原因。不增加强制停止按钮。
- 五项状态：MySQL、Redis、Kafka、消息消费者、弹幕服务。区分未运行、启动中、就绪、停止中、已停止、失败和无法确认，标注本次启动或复用已有实例。
- 一句当前进度，例如“正在等待 Kafka 就绪”。失败时指出具体组件、简短原因和下一步。
- 可折叠的错误详情，只展示经脱敏的有限日志尾部，提供本机日志文件位置。页面不读取任意路径，也不展示连接口令。

已有“互动连接”状态只描述 WebSocket，会与“后端状态”分开，避免把已启动误认为已连接房间。无需另加自动连接或自动重连。收到停止中的状态后，属于被停止服务的页面禁用发送和加入房间；浏览器断开最终仍以实际 WebSocket 事件为准。

通过启动器提供的页面显示管理区域。原有 8080 页面以及 Vite 开发/预览页面继续保留；同源能力探测失败时不显示管理按钮，也不跨域寻找控制服务。

## 结构与默认选择

以下是助手提出的实现选择，可在设计确认时调整：

- 新增 `cmd/launcher`，使用 Go 和现有依赖。一个进程托管 `web/dist` 和本地控制 API，不常驻 Node.js。
- 启动器固定监听 `127.0.0.1:4174`，避免占用当前 Vite 预览的 4173。WebSocket 仍连接 `127.0.0.1:8080`，现有端口输入逻辑不变。本轮管理的业务服务端口固定为 8080。
- CMD 仅作为双击入口，PowerShell 负责读取本机配置、解密连接配置、隐藏启动器窗口并打开页面。后台程序使用明确的可执行文件与参数列表启动，不拼接执行来自网页的命令。
- 运行已编译的 `launcher.exe`、`server.exe`、`consumer.exe`，不把 `go run` 编译进程长期保留在启动链路里。提供独立的串行准备/更新脚本；缺少产物时明确提示运行该脚本。正常点击按钮不安装依赖、不联网下载、不编译。
- 不直接调用原来的基线构建、格式化或压测脚本；仅复用已核对的本机二进制位置和服务配置参数。

## 本机配置与首次准备

- 可提交无敏感值的示例配置；实际配置放在 `.local/` 并加入 Git 忽略。记录 Go、MySQL、Redis、Java、Kafka 的绝对路径、服务配置文件路径及构建目录。本机路径不写入通用代码。
- 首次配置在本机交互输入完整 `DANMAKUFLOW_MYSQL_DSN`，使用 Windows 当前用户绑定的 DPAPI 加密保存。以后由入口脚本解密到进程环境，业务子进程继续使用同名环境变量。页面不负责收集密码。
- 原有环境变量配置可优先使用；不恢复内置账户密码，不将 DSN 放入命令行、URL、日志或 Git。基础设施子进程不继承不需要的数据库口令。
- 更新加密保存的 DSN 后，需要重新打开启动器以读取新环境；页面的“重试启动”不会改变当前启动器已继承的凭据，也不会重配已运行的业务进程。
- 用户必须明确选择数据库，建议独立开发数据库；禁止默认猜测并使用现有业务库。没有配置时页面显示“需要完成本机配置”，不启动业务服务。
- MySQL 数据目录与 Kafka 存储应已初始化。缺失时说明如何单独准备，不运行 `mysqld --initialize`、Kafka storage format、建库或迁移命令。
- `cmd/migrate` 保持独立；缺表时显示可复制的初始化指引，不提供静默执行或清空数据入口。
- Kafka 的目标 topic 必须可用；没有 topic 或 leader 时提示单独创建/修复，不在状态查询中自动创建 topic。

## 启动顺序与状态依据

操作按顺序执行，限制瞬时资源使用：

1. 取得启动互斥锁，校验配置、文件、构建产物及端口占用。预先发现明显冲突，不启动重复实例。
2. 启动或复用 MySQL；使用明确 DSN 建立连接，并复用 `OpenDB`、`CheckSchema` 做只读检查。检查后关闭临时连接。
3. 启动或复用 Redis，通过客户端 PING 确认可用。
4. 启动或复用 Kafka，通过已有 Go Kafka 客户端检查 broker metadata、目标 topic 与 leader；不为了轮询而反复启动 JVM 命令行工具。
5. 确认固定消费组 `danmaku_group_v1` 没有未知消费者后，启动或复用本配置对应的消费者。无法确认已有成员身份时停止该步骤，提示处理冲突，不再启动第二个消费者。
6. 启动或复用本配置对应的 Go 弹幕服务；确认监听成功并能提供预期 HTTP 响应。

消费者现有的 `Ready to process messages` 日志发生在加入消费组之前，不能作为已就绪依据。增加仅供本机启动器使用的可选就绪标记：进程 ID、随机运行 ID、组件、阶段；消费者取得非空分区分配并启动工作循环后才报告就绪，Cleanup/退出时撤销。服务端监听成功后报告就绪。标记不包含 DSN，使用临时文件原子替换，进程身份和运行 ID 必须匹配；单独从命令行启动时不要求标记。

所有等待都有截止时间，默认 MySQL 30 秒、Redis 10 秒、Kafka 90 秒、两个业务进程各 30 秒。超时后停止后续步骤，显示失败，不无限等待、不自动重启。默认值可以由实现者依据本机启动证据适当调整并记录。

“后端已就绪”表示依赖探测、监听和消费者分区分配完成，不保证随后每条消息成功落库。持续状态在单一后台任务中采集，多个标签页共享缓存；页面仅查询缓存，不为每个请求新建数据库连接或 Kafka 客户端。就绪后定时检查进程及必要依赖，退出、失去分区或依赖探测失败时撤销就绪状态。

## 重复启动、资源和失败

- 同一配置只运行一个启动器、一个 MySQL、一个 Redis、一个 Kafka、一个 server 和一个 consumer；多标签页同时点击也只触发一条启动流程。
- 用进程句柄及 PID、创建时间、可执行文件、配置标识核对归属；持久化状态只是线索，不能仅凭旧 PID 判定身份。不按 `java.exe`、`node.exe` 等进程名批量操作。
- 已有依赖通过对应协议检查且匹配所配置实例时复用，不归启动器管理；端口被其他程序占用、实例身份不明时显示冲突，不杀进程或静默换端口。
- 已有 Go 业务进程只有匹配配置和本机运行记录时复用；未知实例阻止启动。数据库口令不得出现在身份标识里。
- 失败时不启动后续组件，不自动停止已就绪组件；页面明确列出哪些仍在运行。用户修复配置后重试，仅启动缺少的组件。
- 复用当前单节点 Kafka 的 192 MiB 最大 Java 堆、64 MiB direct memory 限制、2 个可见处理器，以及 Redis 32 MiB 数据内存上限；这些都不代表进程总内存上限。Go 业务进程使用 `GOMAXPROCS=2`。不启动压测进程或第二套基础设施。
- 日志分组件保存在被 Git 忽略的本地目录，设置轮转/大小上限；网页仅返回固定组件对应的尾部日志，避免无限积累或任意文件读取。
- 启动与停止共用一个操作锁。启动中不接受并行停服请求；启动成功、失败或超时后可以停止已经由启动器创建的实例。停止失败且流程未完成时，禁止重新启动同一组业务实例；先重试完成停止，避免半关闭状态被认作可复用。
- 本轮不加入自动重启、开机自启或守护重启。刷新、关页面、启动器失联均不触发停服。
- 若本机应用控制阻止执行 Go 程序，显示明确错误并停在该步骤，不绕过系统策略；不能承诺在此限制未解除时仍可启动。

## 停服归属与步骤

“本次启动”指这一轮由启动器实际创建的进程，并记录所属运行 ID；不包括开始操作之前就存在、仅被复用的服务。刷新页面不改变归属；启动器重启只能恢复同一运行记录、身份仍匹配的进程，不能认领未知进程。停止前再次核对句柄或 PID、创建时间、程序和配置；任一不符则跳过并报告。

页面可直接说明本轮会停止哪些组件、哪些因已存在而保留，不增加每次操作的确认弹窗。已启动服务可能存在部分失败，这种情况下停止也只处理已经记录的自有进程。存在仍运行的非自有业务进程时，保留它所依赖的自有基础设施并说明原因，避免通过关闭依赖间接破坏保留服务。

正常停止顺序如下，每一步须收到明确完成结果后才继续：

1. **弹幕服务停止接收新工作**：拒绝新连接和新消息，关闭已有 WebSocket 的输入，等待正在处理的回调结束，再处理已进入服务端队列的消息。刷新剩余点赞增量，等待 Redis 操作结束，关闭 Kafka producer 并等待待发送消息的最终结果。退出房间订阅、广播工作循环，关闭连接池，报告停止结果。
2. **消费者完成剩余工作**：在本轮生产者停止后记录 topic 各分区的停止目标位置，消费者继续工作至该位置的有效消息已落库且位点提交得到确认，再停止接收、排空已接收的队列、退出消费组并关闭数据库连接。没有本轮生产者时，只对停止请求时的固定位置负责，不追赶其他生产者无限产生的新消息。若消费者本来就存在，则不操纵该消费者；保留它需要的 Kafka/MySQL。
3. **关闭自有基础设施**：依次请求 Kafka、Redis、MySQL 正常关闭并等待对应进程退出；复用的实例跳过。只有业务处理完成，且没有本次已知的保留业务依赖它时，才关闭该组件。
4. **保留本地启动器与页面**：显示“本次启动的服务已停止”，或“部分服务保留/停止未完成”，不能把还有自有服务运行的情况显示为全部停止。

默认停服等待上限：弹幕服务 30 秒、消费者追赶/排空 60 秒、Kafka 60 秒、Redis 15 秒、MySQL 30 秒。超时是控制操作的失败边界，不是杀进程的计时器：保留尚在运行的组件和它的依赖，展示原因，可重试继续同一退出流程。若进程已退出但结果不明确、退出码异常或消息处理报告失败，显示“异常退出/结果未确认”，不要推进依赖关闭，也不宣称安全完成。

不会调用 `taskkill /F`、`Stop-Process -Force` 或等价强杀作为正常路径；不按进程名批量操作，不在停服时删除数据库、Kafka 数据或缓存目录。

## Go 退出处理的必要修改

本次设计包含以下与有序停服直接相关的改动，以独立小提交实现；不扩展成通用可靠性重构：

- 服务端从阻塞式 `r.Run` 改为受生命周期管理的 HTTP server。单独管理 WebSocket 的关闭和读写协程，处理注册/注销/发送与退出同时发生的情况，避免向已结束的管理循环永久阻塞。HTTP `Shutdown` 本身不会等待 WebSocket，不能只加这一行就标记完成。[Go 1.25 官方文档](https://pkg.go.dev/net/http@go1.25.0#Server.Shutdown)
- Manager 拥有可取消的生命周期、已接收任务计数和有限等待。先禁止新任务，再等待既有生产者停止入队，最后排空消息和工作队列；不能通过直接关闭仍可能被写入的通道退出。点赞收尾独立于“房间是否还有在线连接”，不因关闭最后一个连接而漏掉尚未刷出的增量。
- Kafka producer 关闭时仍消费结果通道并汇总失败。已知发送失败需在停服结果中体现；不能把关闭函数返回或进程退出等同于所有消息写入成功。[Sarama v1.46.3 producer 接口](https://pkg.go.dev/github.com/IBM/sarama@v1.46.3#AsyncProducer)
- 消费者保留批量写库，将位点确认移到对应批次写入成功后；同一分区只确认连续已处理的位置。写库失败不能丢弃批次并越过它确认更高位点，暂停推进并报告错误。对无效/非弹幕消息的既有忽略规则也按顺序处理，避免跳过前面的待落库消息。
- 消费者每个消费会话使用独立队列；结束入队后由唯一负责方关闭并排空，避免重平衡后复用已关闭通道。最终刷库使用独立、有限的排空上下文，不直接沿用已取消的 session context。等待位点提交确认及 consumer group 退出后才报告正常结束。[Sarama v1.46.3 consumer 接口](https://pkg.go.dev/github.com/IBM/sarama@v1.46.3#ConsumerGroupSession)
- 停止请求通过只对本机启动器启用的私有控制通道送达 Go 子进程，匹配运行 ID 和当前用户权限；与正常信号入口汇合到同一幂等退出逻辑。具体 IPC 实现留给实现者选择，不在 8080 业务 API 增加公开停机接口，不以关闭 stdin 或父进程消失作为停服命令。

这一修改提供可检查的正常退出流程，不承诺断电不丢失、故障下消息恰好一次或恢复后没有重复。浏览器 `send()` 仍不是消息送达确认；停服只对服务端已接受的工作负责。写库成功但位点未提交的故障窗口仍可能导致重放，不在本轮增加去重表或事务消息平台。

当前 Redis 配置未开启持久化；其在线数和点赞数在 Redis 退出后不保证保留，页面在停止范围提示中明确说明。MySQL 中已落库的弹幕不因正常停服被删除；Kafka 数据目录也保留。停服设计不静默改变 Redis 的持久化配置。

## Windows 基础设施退出适配

为每种依赖实现固定的停止适配器，执行前核验自有实例身份，执行后等待该实例退出。任何权限不足或停服机制不可用都显示具体错误并保留进程，不临时提权、不扩大到其他实例。

- **Kafka 和 MySQL**：创建时使用各自独立的隐藏控制台，保留进程句柄，不与启动器、终端或其他服务共享控制台。MySQL 保留 `--console`，Kafka 保留控制台 JVM，不能使用会失去这一关闭机制的 `javaw`、`-Xrs`、`CREATE_NO_WINDOW` 等方式。
- 停止时使用同一程序的短生命周期 Windows helper 模式，附加到目标的专用控制台，核对成员仅有目标进程与 helper；helper 屏蔽自身的 Ctrl+C，向这一专用控制台发送 `CTRL_C_EVENT`，然后退出。主启动器等待原进程句柄确认结束。控制台共享、归属不明或无法附加时不发送事件，显示错误。Ctrl+C 不能按任意非零进程组隔离发送，因此不能附加到已有服务所在的未知控制台。[Microsoft 控制事件文档](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent)
- Java 的 Ctrl+C 会触发 JVM shutdown hooks，而 Ctrl+Break 用于线程栈诊断，不能拿它代替 Kafka 停服。Kafka 已有 shutdown hook 负责关闭服务；本轮只触发原生退出，不改 Kafka。[Java 21 信号说明](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html#extra-options-for-java)、[Kafka 4.1.2 官方入口](https://github.com/apache/kafka/blob/4.1.2/core/src/main/scala/kafka/Kafka.scala)
- MySQL 8.4.13 在 `--console` 模式安装控制处理器，Ctrl+C 进入有序关闭路径，因此不要求业务 DSN 额外拥有 SQL `SHUTDOWN` 权限。服务仍在早期初始化、未能处理事件时继续等待到上限或报告未停止，不强杀。[MySQL 8.4.13 官方源码](https://github.com/mysql/mysql-server/blob/mysql-8.4.13/sql/mysqld.cc)
- **Redis**：通过与核验过的自有实例保持的同一连接发送普通 `SHUTDOWN`，按当前持久化配置退出，再等待对应进程结束；关闭命令禁用自动重连和重试，避免端口被新实例接管后误停其他进程。不能加 `FORCE`、`NOW` 或静默改成 `SAVE`。需要确认连接断开来自预期退出，不能只因网络错误就显示已停止。MSYS2 版本返回的 Redis 进程 ID 不直接当作 Windows PID，归属使用原生进程句柄、创建时间和端口监听关系。[Redis SHUTDOWN 文档](https://redis.io/docs/latest/commands/shutdown/)

helper 仅在停止瞬间存在，不为每个服务增加常驻包装进程。已有 Kafka Windows stop 脚本按命令行匹配并删除进程，不复用。启动器只管理其创建的控制台子进程；原本作为 Windows Service 等方式运行的实例继续视为外部实例，不尝试停止。启动尚未到达可确认处理正常退出请求的阶段时，不能用控制事件试探；显示“初始化未完成，暂未停止”，保留进程并允许稍后重试。

## 控制接口边界

控制接口仅存在于本地启动器，不挂入业务服务器。固定提供能力/会话查询、状态查询、POST 启动和 POST 停止操作，无任意命令、任意路径、任意服务或数据库配置写入接口。

只监听 IPv4 回环地址；检查精确 Host 与 Origin，拒绝不符合预期的来源，不启用宽松 CORS。启停操作要求会话随机令牌与自定义请求头；令牌通过受同源约束的接口交给当前页面，保存在内存，不进 URL 或日志。不能仅依赖“端口是 localhost”作为操作系统进程的保护。

按钮会发起真实本机服务启动或停止；GET 页面、GET 状态、刷新和打开标签页都不能触发这些操作。

## 验证与实施边界

设计阶段不启动任何依赖、不连接现有数据库、不改变当前预览进程。本设计通过后才进入实施计划；测试仍优先采用串行、受资源限制的模拟方式。

必要验证：

- 假进程与假协议探测：顺序、超时、失败中止、重复点击、多标签并发、已有实例复用、未知端口/消费组冲突、旧 PID 与伪造就绪文件。
- 停止归属与保护：混合自有/复用实例、启动器重启后的身份核验、部分启动失败后的停止、保留业务的依赖、重试停止、超时不强杀、异常退出不宣称完成。
- Go 生命周期模拟：停服期间拒绝新连接、已有 WebSocket 结束、队列排空、最后一批点赞、producer 发送失败、消费者写库前不确认位点、失败批次不被后续位点越过、重平衡与停止并发、消息已经落库但位点确认失败。
- 模拟 SQL：只读检查、不自动迁移、不写数据，保留现有数据库保护测试。
- 前端模拟管理 API：首次未配置、逐项启停、失败原因、重试、全就绪、停止超时、保留已有实例、启动器失联，以及普通 8080 页面不出现不可用按钮。
- 本地控制 API：来源/令牌校验、固定动作和日志脱敏、GET 无启停副作用。
- Windows 控制台适配：先用隔离的短命测试进程验证隐藏控制台、Ctrl+C、身份核对、未知控制台拒绝和超时保留。可在 Windows CI 串行执行，不用真实 MySQL/Kafka 充当测试替身；本机策略阻止时不绕过。
- 单进程编译与已有前端回归；本机不能执行的 Go 测试继续使用隔离 CI，不绕过 Windows 策略。
- 首次真实启动和双页面互动需要明确的运行授权与选定数据库。仅批准设计不等于授权连接用户现有数据库，也不恢复压测。

实施按设计记录、Go 服务端退出、消费者批次与退出、本机入口和实例归属、启停编排、页面接入、验证与文档分别组织小提交，保留已有提交历史。
